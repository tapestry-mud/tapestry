# Events

## Overview

Tapestry has two distinct event channels that serve different purposes.

`EventBus` is the general-purpose pub/sub channel for game-logic events.
Packs and server-side modules subscribe handlers identified by a string event
type; handlers fire synchronously and in-process during `Publish`. Priority
controls dispatch order and handlers may cancel further processing by setting
`Cancelled = true` on the event object.

`SystemEventQueue` is a lock-free FIFO queue for infrastructure signals
(connect / disconnect). Producers enqueue from any thread; the queue is drained
once per game-loop tick, not on the publishing thread.

## Behavior

### GameEvent shape

- `GameEvent` is defined in `Tapestry.Shared` and carries `Type` (required),
  optional `SourceEntityId`, `TargetEntityId`, `RoomId`, `SourceEntityName`, a
  lazy `Data` dictionary (`Dictionary<string,object?>`), a `Timestamp` set at
  construction, and a mutable `Cancelled` flag.
  (src/Tapestry.Shared/GameEvent.cs:4-18)

### EventBus -- subscribe / unsubscribe

- `Subscribe(eventType, handler, priority=0)` returns an integer subscription
  ID generated by `Interlocked.Increment` from a per-instance counter.
  (src/Tapestry.Engine/EventBus.cs:25-58)
- Subscription state is guarded by a single `object _sync` lock for all
  mutations. (src/Tapestry.Engine/EventBus.cs:12)
- `Unsubscribe(id)` scans all priority buckets and, if found, removes the
  subscription and invalidates the handler cache for that event type.
  (src/Tapestry.Engine/EventBus.cs:60-86)

### EventBus -- priority ordering

- Handlers are stored per event type in a `SortedList<int, List<Subscription>>`
  whose comparer sorts descending (`b.CompareTo(a)`), so higher numeric priority
  values fire first. (src/Tapestry.Engine/EventBus.cs:44)
- Within the same priority value, handlers fire in registration order because
  each priority bucket is a `List<Subscription>` appended to in sequence.
  (src/Tapestry.Engine/EventBus.cs:48-53)
- The default priority when none is supplied is 0.
  (src/Tapestry.Engine/EventBus.cs:25)
- Tests confirm dispatch order: priority 100 fires before 50, which fires before
  10. (tests/Tapestry.Engine.Tests/EventBusTests.cs:34-40)

### EventBus -- wildcard subscriptions

- Subscribing with event type `"*"` adds the handler to a separate
  `_wildcardHandlers` list rather than the per-type map.
  (src/Tapestry.Engine/EventBus.cs:30-38)
- Wildcard handlers are merged with specific-type handlers by priority when the
  handler cache entry is built for an event type; the resulting sorted array is
  stored in `_cache` and reused on subsequent publishes until the cache is
  invalidated. They participate in the same priority ordering as specific-type
  handlers. (src/Tapestry.Engine/EventBus.cs:109-120)
- Adding a wildcard subscription clears the entire handler cache so subsequent
  publishes rebuild merged handler arrays that include the new wildcard.
  (src/Tapestry.Engine/EventBus.cs:35)
- Tests confirm a wildcard handler fires for unrelated event types and that
  adding a wildcard after an initial publish still fires on the next publish.
  (tests/Tapestry.Engine.Tests/EventBusTests.cs:68-75, 122-134)

### EventBus -- publish mechanics

- `Publish` is synchronous and blocking; it iterates the pre-built handler
  array and invokes each handler on the calling thread.
  (src/Tapestry.Engine/EventBus.cs:88-107)
- Before each handler invocation the loop checks `evt.Cancelled`; if true, all
  remaining handlers in the array are skipped without being called.
  (src/Tapestry.Engine/EventBus.cs:94-97)
- Handler errors are caught, logged at Error level (with event type and
  subscription ID), and do not abort iteration -- subsequent handlers still
  fire. (src/Tapestry.Engine/EventBus.cs:98-106)
- A test confirms: first handler throws, second handler still fires.
  (tests/Tapestry.Engine.Tests/EventBusTests.cs:137-154)
- A test confirms: first handler sets `Cancelled = true` and then throws;
  second handler does NOT fire (cancellation is checked before each handler,
  not after exceptions). (tests/Tapestry.Engine.Tests/EventBusTests.cs:157-175)
- Because `Publish` invokes handlers on the calling thread, and a pack handler
  runs script in the process-wide `Jint.Engine` that has no synchronization of
  its own, a publish is only safe on the game loop. `LoopAffinity` marks the
  span of `GameLoop.Tick` with a thread-static flag; `Tick` is synchronous, so
  the flag is exact even though `RunAsync` resumes on a different pool thread
  each iteration. (src/Tapestry.Engine/LoopAffinity.cs:20-44,
  src/Tapestry.Engine/GameLoop.cs:136-151)
- The script event dispatcher checks that flag and logs an Error naming the
  event type when it is invoked off the loop while the loop is running. It does
  not redirect the call -- it only reports it, because the underlying failure
  raises from inside Jint's own call machinery rather than from the pack.
  An engine that has never ticked (unit tests, boot) does not trip it.
  (src/Tapestry.Scripting/Modules/EventsModule.cs:75-88)
- Publishers that run off the loop must post through `GameLoop.Schedule`, which
  drains at the top of the next tick. Game entry does this for
  `character.created`, `player.login` and `player.reconnect`.
  (src/Tapestry.Server/GameEntry/GameLoopEntrySpawner.cs:23-52)
- Tests confirm scheduled work reports itself as on-loop, the flag does not
  leak past its tick, and a thread running concurrently with a tick does not
  inherit it. (tests/Tapestry.Engine.Tests/LoopAffinityTests.cs:26-79)
- Nested `Publish` calls (a handler publishes a new event) are safe because
  each `Publish` call captures its own snapshot array before iteration.
  (src/Tapestry.Engine/EventBus.cs:90; tests/Tapestry.Engine.Tests/EventBusTests.cs:179-195)

### EventBus -- handler cache

- After building a merged handler array for an event type, the result is stored
  in `_cache` (`Dictionary<string, Subscription[]>`).
  (src/Tapestry.Engine/EventBus.cs:11, 117-120)
- The cache entry for a specific event type is invalidated whenever a
  specific-type subscription or unsubscription occurs for that type.
  (src/Tapestry.Engine/EventBus.cs:54, 76)
- Adding or removing a wildcard subscription clears the entire cache because
  wildcards affect every event type. (src/Tapestry.Engine/EventBus.cs:35, 82)

### SystemEvent and SystemEventQueue

- `SystemEvent` is an abstract base with a UTC `Timestamp` set at construction.
  Concrete subtypes `ConnectEvent` and `DisconnectEvent` carry `SessionId`,
  `EntityId`, and a `SpawnRoomId` or `Reason` string respectively.
  (src/Tapestry.Engine/SystemEvent.cs:1-34)
- `SystemEventQueue` wraps a `ConcurrentQueue<SystemEvent>` and exposes
  `Enqueue` and `DrainAll`. `DrainAll` dequeues all pending events into a new
  `List<SystemEvent>` and returns it. (src/Tapestry.Engine/SystemEventQueue.cs:1-25)
- The queue is registered as a singleton.
  (src/Tapestry.Engine/ServiceCollectionExtensions.cs:63)
- The game loop drains the queue in phase 2 of each tick (after scheduled
  actions, before command processing). Each drained event is dispatched via
  `OnSystemEventProcessed` and, for `DisconnectEvent`, via `OnDisconnect`.
  (src/Tapestry.Engine/GameLoop.cs:172-199)
- `PlayerSpawner` enqueues `DisconnectEvent` when a session disconnects or
  errors; the game loop also enqueues `DisconnectEvent` for idle-timeout
  expiry. (src/Tapestry.Server/PlayerSpawner.cs:108, 163;
  src/Tapestry.Engine/GameLoop.cs:390, 408)
- `DisconnectEvent` deduplication: the game loop tracks in-progress disconnects
  in `_activeDisconnects`; duplicate events for the same entity are skipped.
  (src/Tapestry.Engine/GameLoop.cs:183-187)

### Pack JS API (EventsModule)

- Packs subscribe to events via `events.on(eventType, callback)`. The callback
  is dispatched via `engine.Invoke`, which runs the function inside the calling
  module's scope; attribution is lexical via `JintRuntime.GetActivePack()` at
  invocation time. No `__currentPack` global is captured at registration.
  (src/Tapestry.Scripting/Modules/EventsModule.cs:24-28)
- No priority argument is exposed to JS; JS subscribers always use the default
  priority of 0. (src/Tapestry.Scripting/Modules/EventsModule.cs:24-28)
- The JS event object passed to the callback exposes: `type`, `sourceEntityId`,
  `targetEntityId`, `roomId`, `cancelled`, `data`, and a `cancel()` function.
  (src/Tapestry.Scripting/Modules/EventsModule.cs:76-83)
- `cancel()` sets `Cancelled = true` on the underlying `GameEvent`, which stops
  subsequent handlers on the next cancellation check.
  (src/Tapestry.Scripting/Modules/EventsModule.cs:66-69)
- Packs publish events via `events.publish(eventType, dataObj)`. Properties of
  the JS object are extracted into the `Data` dictionary; no entity IDs are
  set. (src/Tapestry.Scripting/Modules/EventsModule.cs:33-49)
- There is no dedicated rate limit on pack event publishing via the event bus;
  pack event handlers are subject only to the engine-wide Jint execution
  timeout (JintRuntime.cs:29-31).

### IGameModule and server-side event wiring

- `IGameModule` declares a `Name` string property and a `Configure()` method.
  The contract contains no event-specific logic -- it is a general bootstrap
  hook. (src/Tapestry.Contracts/IGameModule.cs:1-7)
- At startup `GameBootstrapper.Configure()` iterates all registered
  `IGameModule` implementations and calls `Configure()` on each.
  (src/Tapestry.Server/GameBootstrapper.cs:8, 24)
- `WorldEventModule.Configure()` calls `Subscribe` for `player.moved`,
  `progression.level.up`, `entity.vital.depleted` (at priority 50), and
  `combat.engage`, and delegates stat-growth wiring to
  `StatGrowthOnLevelUp.Subscribe`. (src/Tapestry.Server/Modules/WorldEventModule.cs:43-48)
- Multiple server-side modules are registered as `IGameModule` singletons:
  `ConfigurationModule`, `ContentLoadingModule`, `QuestStartupModule`,
  `CombatEventModule`, `WorldEventModule`, `TickHandlerModule`,
  `PersistenceModule`, `PlayerInitModule`, `BadInputModule`.
  (src/Tapestry.Server/Program.cs:164-176)

### Vitals mutation event

- `VitalsService` is the sole publisher of `entity.vital.changed`: `Apply`, `Set`, and
  `RestoreToMax` clamp an entity's hp/resource/movement write and publish this event only
  when the clamped value actually changes. Data shape: `{ vital, old, new, delta, reason }`.
  It is a separate signal from `entity.regen`, `entity.vital.depleted`, and `combat.hit`,
  which still fire for their own original purposes; GMCP's vitals batching and combat
  target-bar refresh subscribe to `entity.vital.changed` alone. See combat-resolution.md,
  rest-and-recovery.md, abilities.md, and gmcp.md for the subsystems that write vitals
  through it and the handlers that subscribe to it.
  (src/Tapestry.Engine/VitalsService.cs:22-67)

### Status mutation event

- `EntityStatusBroadcaster` (an `IPropertyObserver` registered on every tracked entity via
  `World`) publishes `entity.<topic>.changed` when `Entity.SetProperty` changes a key that
  `PropertyRegistry.TryGetObservableTopic` resolves to a topic. Data shape: `{ key, old,
  new }`. `CommonProperties.Register` declares `sustenance` and `alignment` observable on
  the `status` topic, so a change to either publishes `entity.status.changed`;
  `CharStatusHandler` subscribes to it and resends `Char.Status`. Distinct from
  `entity.vital.changed` above -- vitals are a dedicated typed store (hp/resource/movement)
  written through `VitalsService`, while this seam covers the general dynamic property bag.
  See persistence.md for `RegisterObservable`/`TryGetObservableTopic` and gmcp.md for the
  GMCP consumer. (src/Tapestry.Engine/EntityStatusBroadcaster.cs,
  src/Tapestry.Engine/CommonProperties.cs:52-56, Handlers/CharStatusHandler.cs:53-59)

## Related capabilities

Specific event types fired by combat, movement, progression, GMCP, and other
subsystems are covered in those subsystems' capability specs, not here.

`ConnectEvent` is defined in `SystemEvent.cs` but has no production enqueue
site; connect handling goes through `PlayerSpawner.CompleteLogin` and
`GameLoop.Schedule` rather than the system-event queue
(src/Tapestry.Engine/SystemEvent.cs:22-28; src/Tapestry.Server/PlayerSpawner.cs:78-139).
